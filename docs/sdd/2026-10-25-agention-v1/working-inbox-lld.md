# Agention v1: Working Inbox LLD

- Status: Built in Delivery 2 (agention#1)
- Date: 2026-10-27
- Governs: plan Delivery 2
- Requirements: FRD R1-R3, R5-R20, R21's thread signals (blocked on you, overdue, status) and its
  quiet and stranded, R24, R25-R29 for threads, R30, R31, R33, R35-R37; rulings 26 to 28 and 31 to
  48; the HLA as amended here.

Delivery 2 makes the inbox usable end to end: an agent registers, starts threads, asks and reads the
answers; the operator signs in with a passkey, sees the asks open to them, and answers. It also
moves the repository to TypeScript (ruling 28), in the layout the
[Repository LLD](repository-lld.md) describes. Sessions' state and presence, groups, tags and
browsing by group are Delivery 3.

This document settles what the HLA left open and does not repeat what the HLA and FRD already say.
Code, tests and public documentation written from it state behavior in their own words, without
requirement or ruling numbers.

## Database

### Opening

The server's database module owns opening, every DDL statement and migrations. The data directory
and database file follow the one private-file rule, which `packages/private-files` holds for the
server and the bridge alike. Symlinks are resolved, and every directory on the real path, from `/`
down, must be a real directory owned by the user or root that no one else can write unless it is
sticky. The directory holding the file is owned by the user and has no group or other bits. The file
itself is never a symlink, is a regular file owned by the user, and has no group or other bits.
Directories are created `0700` and files `0600`. An existing path that breaks the rule is refused,
never repaired; a path where a directory should be that is not one is refused as not a directory;
and a path that cannot be reached is refused as inaccessible, naming the system's error code. The
SQLite header (format, `application_id`) is checked before SQLite opens the file.

`node:sqlite` is built into Node 24 and needs no install script, which the repository disables. Each
process opens one `DatabaseSync` connection. Its API is synchronous, so a transaction is one
synchronous function:

- `transaction(fn)` runs `BEGIN IMMEDIATE`, then `fn`, then `COMMIT`, and rolls back if `fn` throws.
  It throws if `fn` returns a promise, so no transaction can span an `await` and writes never
  interleave in the server process.
- Reads are synchronous statements on the same connection. Data is small and indexed, so they hold
  the event loop for milliseconds at most (the operator's thread list takes about 5 ms over 500
  threads); a long poll waits on the notifier, never in a query.

Pragmas run on open: `journal_mode=WAL`, `synchronous=FULL` (a write an agent was told succeeded
survives power loss; the write rate is tiny), `foreign_keys=ON`, `busy_timeout=5000`. CLI commands
that write while the server runs (`passkey-link`) open their own connection and wait on the busy
timeout.

### Migrations

Migrations are an ordered list of SQL scripts bundled with the server. `PRAGMA user_version` records
how many have run. Opening applies the missing ones, each in its own transaction that also bumps
`user_version`, and refuses a database whose `user_version` exceeds the server's list (written by a
newer release). Migration 1 is this delivery's schema, frozen once 0.1.0 is released; Delivery 3
adds migrations after it and tests them against a database written by this delivery.

### Schema

All tables are `STRICT`. Times are integer Unix milliseconds (UTC). Text columns hold exactly what
was submitted. The shape and the invariants are fixed here; column names may change in code review.

```text
people          id, name, created_at
agents          id, name UNIQUE, created_at
sessions        id, agent_id, name, last_pos, last_seen_at NULL, created_at; UNIQUE(agent_id, name)
actors          id, session_id UNIQUE NULL, person_id UNIQUE NULL; exactly one set

registrations   id, public_key UNIQUE, proposed_agent, proposed_session,
                status, session_id NULL, created_at, expires_at, decided_at
passkeys        id, person_id, credential_id UNIQUE, name, data, created_at, last_used_at
browser_sessions hash PK, person_id, passkey_id, csrf_token, created_at, idle_expires_at,
                absolute_expires_at
instance        id (always 1), challenge_key (32 random bytes, made by migration 1),
                name NULL (set once by the first `agention serve` to listen, never changed after)
used_challenges hash PK, expires_at
passkey_links   hash PK, operator_name, expires_at

threads         id, session_id, number, requester_actor_id, audience_actor_id, title, created_at,
                last_seq; UNIQUE(session_id, number)
messages        thread_id, seq, session_id, session_pos, actor_id, registration_id NULL,
                created_at, request_id, digest, text, detail, message_references, replaces_seq,
                topic; PRIMARY KEY(thread_id, seq), UNIQUE(session_id, session_pos),
                UNIQUE(actor_id, request_id), UNIQUE(thread_id, replaces_seq)
asks            thread_id, number, seq, question, suggestions, multiple, impact, priority, effort,
                answer_by, fallback; PRIMARY KEY(thread_id, number)
answers         thread_id, seq, ask, declined, picks, text; PRIMARY KEY(thread_id, seq, ask)
withdrawals     thread_id, seq, ask, reason; PRIMARY KEY(thread_id, seq, ask)
thread_marks    actor_id, thread_id, read_seq, archived_seq;
                PRIMARY KEY(actor_id, thread_id)

live_messages   view: messages that no later message replaces
open_asks       view: asks on live messages that no live message answers or withdraws
thread_titles   FTS5 index of threads.title (external content; unicode61, diacritics removed)
```

Identity:

- `people` holds at most one row in v1 (its `id` is checked to be 1), the operator, created by the
  first passkey link with the name it is given (the name grammar below; default `operator`); that
  name labels the operator's messages. `thread_create` sets the audience to this person's actor. No
  agent can hold a credential before the operator exists, because only the operator approves
  registrations.
- Messages, marks and thread roles reference `actors`, so roles stay independent of who an actor is.
  The actor row is created with its session or person.
- Names are 1 to 63 characters of `[a-z0-9_-]` starting with a letter or digit, so they appear in
  URL paths and directory names unescaped.

Credentials:

- A registration is one agent credential. `status` is `pending`, `approved`, `rejected` or
  `revoked`; a pending registration past `expires_at` is shown as expired and cannot be approved.
  `session_id` is set exactly when approved or revoked (checked). A registration the operator
  decided is never deleted; one that expired while pending is deleted, since nothing refers to it.
- `public_key` is the base64url form of the raw 32-byte Ed25519 public key, which its tokens carry
  as `kid`.
- Every other secret (browser session, challenge handle, link) is 256 random bits stored only as its
  SHA-256, so a fast hash is enough.

Threads and messages:

- A thread stores only what never changes (`title`, roles, `created_at`) and `last_seq`, its latest
  message; a `BEFORE UPDATE` trigger aborts any change but to `last_seq`. Everything else derives
  from its messages through the two views, which carry the HLA's `live` and `open` definitions in
  one place for every query.
- `thread_titles` indexes each title for search. An `AFTER INSERT` trigger on `threads` fills it,
  and the index relies on titles never changing, which the trigger above enforces; threads are never
  deleted. Search reaches messages' text and detail later through a second index beside it.
- `message_send`'s schema requires at least one of text, references, asks, answers, withdrawals, a
  topic or a replacement; a thread's first message may carry none, since the title speaks for it. A
  message that only replaces another retracts it, which the rules below refuse while that message
  holds an open ask or withdrew one. Since asks and answers are rows of their own, the schema at the
  boundary enforces this, and the store writes a message and its rows in one transaction.
- An `asks` row belongs to the message `(thread_id, seq)`, only a requester's (the store checks).
  `number` counts from 1 within the thread in the order asks are written, a message's own in the
  order given, each one past the thread's highest so far; nothing renumbers an ask, and a
  replacement's asks are new rows with new numbers. `question`, `suggestions`, `multiple`, `impact`
  and `priority` are required; `effort` (`quick`, `under_15m`, `under_1h` or `longer`), `answer_by`
  and `fallback` are optional. `suggestions` is a JSON array of `{label, description}`, possibly
  empty; `multiple` needs at least two (checked). The schema's defaults are impact `none`, priority
  `normal`, multiple false and no effort.
- An `answers` row belongs to the message `(thread_id, seq)` and names the ask it answers by its
  number, `ask`, a foreign key into `asks`; the store checks that the ask is an earlier message's.
  The primary key lets a message answer each ask once. `declined` is 0 or 1. `picks` is a JSON array
  of suggestion indexes and `text` the answerer's own words (the "Other" choice, or the whole answer
  to an ask without suggestions), each null when absent; a decline has neither, and any other answer
  has at least one (checked). Reads return the picked labels beside the indexes.
- A `withdrawals` row belongs to the message `(thread_id, seq)`, only a requester's (the store
  checks), and names an ask by its number, `ask`, a foreign key into `asks`, with `reason`, the
  requester's plain-text explanation, which is required; the store checks that the ask is an earlier
  message's. The primary key lets a message withdraw each ask once. An ask a live message withdraws
  is closed: no longer open, and never answered. Reads return a withdrawn ask's withdrawal as
  `{seq, reason}`.
- `replaces_seq` names an earlier message (`replaces_seq < seq`, checked) by the same actor that
  nothing has replaced yet; the unique index makes a second replacement of one message impossible. A
  replacement is a whole message: it carries again every part it keeps.
- `topic` is null when the message leaves the topic alone. No message clears a topic, but a thread's
  topic is the one the latest live message setting one sets, so replacing the message that set it
  restores the one before unless the replacement carries it again.
- `message_references` is a JSON array of `{label, identifier, url, thread}`, any party's, or null
  when there are none, each with at least one of `identifier`, `url` and `thread`. `thread` is a
  thread number in the same session, checked when the message is written, and displays as a link to
  it.
- Threads are addressed by session and number everywhere
  (`/api/agent/s/<agent>/<session>/threads/12`, the web route `/s/<agent>/<session>/threads/12`).
  Numbers count from 1 within a session, so they reveal nothing about other sessions, and references
  to threads stay within one session, so a reference never names a thread its reader cannot see.
- `UNIQUE(actor_id, request_id)` is retry deduplication for creates and messages alike.
- `registration_id` records the credential behind a session actor's message (R1).
- `session_pos` counts the session's messages from 1 (from `sessions.last_pos`, bumped in the same
  transaction). It is the position `message_wait` resumes from, and like thread numbers it says
  nothing about other sessions.
- `BEFORE UPDATE` and `BEFORE DELETE` triggers abort, on this table, on `asks`, `answers` and
  `withdrawals`, and on every later log table.

A store test replays every thread's messages and compares what the views derive (live messages, open
asks, answers, withdrawals, topic, status) and each thread's `last_seq` and session's `last_pos`
with a straightforward fold over the log.

## Store

### Writes

The HLA's write algorithm stands, in the order it gives:

1. Bounds and shape (`invalid_input`), before the transaction opens, so a bad payload never takes
   the write lock. Bounds depend on no thread's state, so this reveals nothing about the target.
   Every route parses its input with the shared schema; store operations take the parsed, typed
   values.
2. Authorization, inside the transaction (`not_found`).
3. Replay: an earlier message by the same actor with the same request id returns its result if the
   digest matches, else `request_id_conflict`. A write's result is the thread number and the new
   message's sequence, so a retry returns exactly the original result and reveals nothing later. The
   digest is SHA-256 over a canonical encoding of the operation, the target (session and thread
   number, or the session for a create) and the payload excluding `seen_through`. A stale write
   appends nothing, so its retry may reuse the request id.
4. Roles (`not_allowed`), which do not depend on the thread's messages: asks, withdrawals or a topic
   need the requester, answers the audience.
5. Staleness: `seen_through` above `last_seq` is `invalid_input`; below it is `stale` with the
   missed messages. Checking this before the message rules means a write overtaken by another
   message always fails as stale, so the web UI's keep-the-draft flow runs (R29).
6. Message rules, against the thread's messages:
   - a replaced message must exist and be live; another actor's message is `not_allowed`, a missing
     or already replaced one `invalid_input`;
   - each answer must name an open ask, except that a replacement must answer again every ask the
     message it replaces answered that is still live, may not answer one its requester since revised
     or retracted, and may answer open asks besides: an answer is changed, never retracted, and one
     to a dead ask goes with the message it rode in. Picks must be distinct and in range; an ask
     without suggestions takes own words and no picks, and one that allows a single answer takes
     exactly one pick or own words, never both;
   - each withdrawal must name an open ask, the replaced message's own included, except that a
     replacement must withdraw again every ask the message it replaces withdrew, its own message
     live or not, with the same reason or a new one: a withdrawal is never undone, and the thread's
     status keeps counting it;
   - a replacement of a message holding open asks must ask again or withdraw each of them: its asks
     and its withdrawals of that message's open asks must together number at least as many as that
     message holds open. One short of that is refused, naming the open asks, so none is dropped
     unexplained (asks are numbered anew, so the count is what the server can check);
   - a reference to a thread must name one in the same session (`invalid_input` for each of these
     but the author check).

After commit, the store notifies waiters on the thread's session.

### Read and archive marks

Marking read, marking unread and archiving move only the caller's own mark. They write no message
and wake no one. A thread's creator and every writer have read through their own message, and a
writer for whom the thread is archived keeps it archived: its archive mark moves to its own new
message.

- Marking read raises `read_seq` to `through` and never lowers it.
- Marking unread from a message lowers `read_seq` to just before it (`from - 1`, with `from` at most
  the thread's latest) and never raises it, so it cannot claim a message the caller has not seen.
  The bridge offers no tool for it, because agents have no use for it.
- Archiving raises `archived_seq` to `through`, carried on over the caller's own messages that
  directly follow it, and never lowers it; archiving all of a thread is archiving through its latest
  message. It is refused (`invalid_input`, naming the ask by number) when an ask open to the caller
  sits at or before `through`, so the operator answers or declines first. A message is archived for
  the caller when it is at or before `archived_seq`. Nothing ever shows one party's archive mark to
  the other.
- Unread means live messages by another actor after both `read_seq` and `archived_seq`: an archived
  message is never unread, so an agent that archives without reading does not wake on it again. A
  retraction is one, so the other party learns of it. A thread is archived for the caller when
  `archived_seq` reaches its latest message: all its messages are archived. Another party's later
  message therefore returns it, and the caller's own keeps it archived by moving the mark. Archiving
  is refused over an open ask, an answer is never retracted, and every new ask arrives after the
  mark, so a thread holding an ask open to the caller is never archived for it.

### Open asks, roll-ups and filters

An ask is open to a thread's audience; to its requester it is awaiting an answer. Every list and
signal is a query over the two views and the caller's mark:

- Roll-ups per thread: the caller's read mark, the unread count, how many live messages it holds
  (`message_count`), the topic (from the latest live message that sets one), the open asks, each by
  its number and its message's sequence, most pressing first (by priority, then blocking, then
  earliest answer-by with none last, then lowest number), the lead ask the sort places it by, and
  from its open asks the count, the earliest, likewise (it has the lowest number), the highest
  priority, the earliest answer-by, and whether any is blocking or overdue; its status, with, while
  it is withdrawn, the latest live withdrawal's ask, reason and message; and on the web mount its
  session's last seen and whether it is quiet, and whether the thread is stranded
  ([Presence](#presence)).
- Status rolls up the thread's counted asks, those on a live message or withdrawn by one: `open`
  while any is open (only one on a live message can be); otherwise `withdrawn` when a live message
  withdraws every one, `answered` when there are any; and `none` when there are none. It depends on
  no viewer, since only the requester asks. A revised ask sits on a replaced message and no live
  message withdraws it, so it plays no part, and its replacement's asks do; an ask a replacement
  withdraws by name counts as withdrawn. A replacement takes its message's asks with it, answered or
  not: one that carries an answered ask again asks it anew, so the thread is open again, and a
  retraction of a message whose asks were answered leaves them out, so the thread can fall from
  answered to none. The latest withdrawal a summary names comes from the same asks.
- A list holds the threads not archived for the caller, and archived ones too with
  `include_archived`. Every other narrowing is a filter. Filters combine with AND; the values given
  for one filter, where it takes several, combine with OR. Each filter keeps the threads that:
  - `search`: have a title holding every word of the search text, each as the start of a word,
    ignoring case and accents (each word is quoted as an FTS5 prefix term, so the text is never read
    as query syntax);
  - `status` (`open`, `answered`, `withdrawn` or `none`): have that status;
  - `priority` (`urgent`, `high` or `normal`), `impact` (`blocking` or `assuming`), `overdue` and
    `effort` (`quick`, `under_15m` or `under_1h`), the ask filters: hold one open ask, asked by the
    caller or of it, that meets every ask filter on (that priority or higher, that impact, past its
    answer-by, and that effort or less, an ask stating no effort meeting no effort filter); any of
    them on keeps only open threads;
  - `unread`: have unread messages, as [Read and archive marks](#read-and-archive-marks) defines
    them;
  - `agent_read` (`unread` or `stranded`): hold a live message by the operator after the session's
    read cursor (the session's archive mark plays no part, since the operator never sees it), and
    for `stranded` while the session is quiet or has no active credential ([Presence](#presence));
  - `agent`, any number of agents: belong to one of them;
  - `session`, any number of sessions, each written `agent/session`: belong to one of them;
  - `topic`, any number of topics, each written `agent/session/topic`: carry one of them (the agent
    mount takes one bare topic, within the session its path names).

  The agent mount takes `include_archived`, `search`, `status`, `unread` and `topic`, within its own
  session; the web mount takes them all.

- Sorts. The web list takes `sort` and `reverse`; the agent mount keeps `priority` in its own order.
  Each sort places a thread with open asks by its lead ask, the one its row shows: of its open asks
  meeting the ask filters, the first in the sort's own order of asks. Every thread without one
  follows by latest message, newest first (a thread's latest message is always live, since nothing
  follows it). Ties in an ask's order break in the priority order of asks.
  - `priority`, the default: by the lead ask's priority, then blocked, then earliest answer-by (none
    last), then oldest by its message's time (within a thread, asks with equal keys go by number).
    Overdue follows from answer-by and is no key of its own, so pages never shift as time passes. It
    ranks the threads with open asks.
  - `due`: threads whose lead ask has an answer-by first, soonest first; then threads with open asks
    and no answer-by among them, in priority order. It ranks those whose lead ask has an answer-by.
  - `effort`: threads whose lead ask states an effort first, least first; then threads with open
    asks stating none, in priority order. It ranks those whose lead ask states an effort.
  - `latest`: every thread by latest message, newest first, the lead ask chosen as for `priority`.
  - `created`: every thread by when it was created, newest first, which within a session is its
    number's order, the lead ask chosen as for `priority`.

  `reverse` reverses the threads the sort ranks, every key and tie among them, and leaves every
  thread it does not rank after them in the order it had. It never changes which ask leads a thread.
  Ties left under any sort break on the session's id, then the thread number, so the order is total.
  A thread holding an ask open to the caller is never archived for it, so including archived threads
  only adds to the rest. A cursor names its sort, `reverse` and grouping and is refused under
  another.

- The web list returns `total`, the threads it holds, which the filter sheet shows.
- Counts. `GET /threads/counts` takes the list's filters and returns, for every value of every
  filter but search, how many threads that value keeps with every other filter as it is, which for a
  filter taking one value is the total the list would hold with that value chosen: status (any,
  open, answered, withdrawn, none); priority (any, normal, high, urgent); impact (any, blocking,
  assuming); due (any, overdue); effort (any, quick, under_15m, under_1h); read (any, unread); read
  by agent (any, unread, stranded); archived (hide, show); for each agent, each session and each
  topic that holds a thread, its own count, whatever that filter's own choices are; and `reset`, the
  total with no filter on. A value of an ask's property counts with status as it is, keeping only
  open threads. Each value is counted by running the list's own total with that value chosen, so the
  rule that one open ask meets every ask filter lives in one place; agents, sessions and topics are
  each counted in one statement, grouped by them, with that filter's own condition off.
- Grouping. With `group` (`session` or `agent`) the list orders its threads by their group, then by
  the sort, so a group's threads arrive together: grouped by session, each session and each topic
  within it is placed by its first thread under the sort; grouped by agent, each agent and each
  session within it likewise. Each page also carries the roll-up of every session the list holds
  and, grouped by session, of every topic within it (a topic absent for threads without one): how
  many threads, how many unread, whether any holds a blocking ask open to the caller, the highest
  open priority, and whether all are archived for the caller, with a session's last seen and whether
  it is quiet. An agent's roll-up composes from its sessions' on the client (sums, any, the highest,
  all; quiet when all are, last seen the latest). A group's place is its first thread's sort keys,
  and a grouped cursor carries them beside the thread's own. A change that moves a group ahead of a
  page's cursor skips that group's remaining threads for the rest of that pass, and one that moves
  it behind repeats them, so a group can arrive in two runs.
- Bulk mark read and bulk archive take each thread with the `through` the list showed, as one
  thread's marks do, so a message that arrived since stays unread and leaves the thread unarchived;
  bulk archive skips threads holding an ask open to the operator and names them.

### Presence

Delivery 2 carries R24's last seen and two of R21's signals (ruling 48); session state, and a
stopped session's part in stranded, come with Delivery 3's envelope.

- `sessions.last_seen_at` is stamped by every authenticated call on the session's routes once its
  credential is approved, and by `register` from an approved key, before the call's own work, and is
  null until the first. The stamp checks the credential is still approved, writes when the clock has
  gone back, and never fails the call: a failed stamp is logged. It is kept to the minute: a call
  writes it only when that moves it a minute or more, so polling writes about once a minute. A
  pending registration has no session, so its calls stamp nothing.
- A session is quiet when it has not been seen within `--quiet-minutes` (default 15) and the minute
  a stamp may lag, so a session calling is never quiet, or when it was never seen.
- A thread is stranded when it holds a live message by the operator after the session's read cursor
  while its session is quiet or has no active credential: the operator wrote, and the agent is not
  there to read it, so the operator knows to resume it. An agent keeps running while it has open
  asks or unread messages (ruling 61), so this shows an agent that stopped anyway, or is busy and
  has not checked.
- Both are computed in queries against the request's clock, never stored, like every signal.

### Bounds

The zod schemas in `packages/api` are the bounds. Lengths count Unicode code points, as JSON
Schema's `maxLength` does. All text must be valid UTF-8 without NUL (a request body that is not
valid UTF-8 is refused, never repaired), and required text needs a character other than white space;
single-line fields also refuse line breaks, other control characters and the invisible characters
that make text read differently from what it holds (bidirectional embeddings, overrides and
isolates, the zero-width space, the word joiner, the byte order mark), and suggested answers must
differ after Unicode normalization.

| Field                     | Bound                                                                                                                                                                                                        |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Title                     | 1-200, single line                                                                                                                                                                                           |
| Message text              | Markdown, 1-1,000; omitted rather than empty                                                                                                                                                                 |
| Message detail            | Markdown, 1-20,000, only beside text; omitted rather than empty                                                                                                                                              |
| Question                  | 1-300, single line                                                                                                                                                                                           |
| Asks                      | 1-10 to a message, omitted rather than empty                                                                                                                                                                 |

and topics, and both say when they leave any out; a thread's roll-up lists at most 50 open asks
beside their count and the earliest; `GET /agents` pages agents and lists at most 500 sessions for
each, saying when it leaves any out.

The body bound covers a message with every field at its bound, every character written as an escaped
surrogate pair (about 2.0 MB with ten asks, ten answers and ten withdrawals at their bounds).

### Errors

One error shape on both mounts and in the bridge's tool errors:
`{"error": {"code", "message", "field"?, "missed"?}}`.

| Code                  | When                                                                       | HTTP status |
| --------------------- | -------------------------------------------------------------------------- | ----------- |
| `invalid_input`       | Bounds, shape or message rules; `field` names the input                    | 400         |
| `unauthenticated`     | Missing, invalid, expired or revoked credential                            | 401         |
| `not_allowed`         | Authorized, but the role, the author or a needed recent sign-in forbids it | 403         |
| `not_found`           | Unknown or unauthorized target                                             | 404         |
| `stale`               | `seen_through` behind; `missed` carries the earliest 50 missed             | 409         |
| `request_id_conflict` | Request id reused with different content                                   | 409         |
| `rate_limited`        | A budget is exhausted                                                      | 429         |
| `internal`            | Anything else; details only in the server log                              | 500         |

`not_allowed` reveals nothing that `not_found` protects, because the caller can already see the
thread. An oversized body gets status 413 with the same shape and `invalid_input`.

## Identity and authorization

The identity module defines `Identity {actor, credential, grants}` and
`authorize(identity, sessionId)`. Two authenticators produce identities:

- on `/api/web/`, a browser session cookie: actor the person, grants every session plus
  administration;
- on `/api/agent/`, a token signed by a registration's key: actor the session the registration was
  approved for, grants that session.

Every store operation takes an `Identity` and a target and calls `authorize` inside its transaction.
`authorize` also confirms the credential is still live (the browser session unexpired; the
registration approved), so authorization, revocation and the data they protect are read in one
snapshot and no layer above re-checks. Store tests cover each operation with an identity granted a
different session, and with a credential revoked between authentication and the operation, expecting
`not_found` and `unauthenticated`.

## Agent authentication

Agention writes both ends, so session keys suffice (rulings 26 and 27): the server stores only
public keys and issues, rotates and stores no token.

### Keys and codes

- The bridge generates an Ed25519 key with `node:crypto`. Its raw 32-byte public key, base64url
  encoded, identifies it everywhere: in the `registrations` table and as the `kid` of its tokens.
- The code is the first 50 bits of SHA-256 over the raw public key, in Crockford base32, grouped
  `XXXXX-XXXXX`. The bridge computes it locally and the server computes it from the stored key.
  Matching codes means the registration the operator approves carries the key the agent holds.
- A submit whose code equals that of another pending registration is refused. An attacker would have
  to see the code the agent relayed and then find a key with the same 50-bit digest, but the genuine
  registration already holds that code while it is pending, so a matching key cannot even be
  submitted.

### Tokens

The bridge mints a token for every request: a compact JWS signed with the session key (`jose`),
header `alg` `EdDSA` and `kid` set to the public key, claims `aud` (the server's origin) and `exp`
(its clock plus 120 seconds). The server:

1. reads `kid` and loads the registration with that key, one indexed read (an unknown key is
   `unauthenticated`, like a bad signature);
2. verifies the signature with the stored public key, accepting only `EdDSA`;
3. requires `aud` to equal the origin, and `exp` to be present, in the future and no more than 300
   seconds ahead of its clock, which tolerates two minutes of clock skew either way;
4. builds the identity; the operation's transaction then confirms the registration is approved and
   grants the session in the path.

A captured token replays for at most a few minutes, inside TLS. No token identifier is stored, and
the bridge never logs tokens. A token for another audience gets a `401` whose message names the
expected origin, so a mistyped `AGENTION_URL` is easy to spot.

### Registration endpoint

`POST /api/agent/registrations` takes the proposed agent and session names, with a token signed by
the key being registered; the server verifies it against the `kid` itself, since the key may be new.
This is the one agent route that accepts a key the operator has not approved.

- A new key creates a pending registration that expires after one hour.
- A key already known creates nothing; the request returns that registration's state, so a retry is
  harmless and the same call reports progress.
- The response is the status, the code, the expiry and, once approved, the granted agent and session
  names.

### Approval and revocation

- The approve request says, for both the agent and the session, whether it names an existing one or
  a new one; a mismatch (a "new" name that exists, an "existing" one that does not) is
  `invalid_input`. Approval may grant other names than proposed. Approving onto an existing session
  shows that the credential gains the session's full history (R5). A session may hold several
  approved credentials; each is revoked on its own.
- The approval screen shows the code, the proposed names and the registration's age, and says to
  approve only a code the agent relayed. The explicit existing-or-new choice keeps the history grant
  deliberate.
- Revoking sets the registration `revoked`, which ends its tokens at once, and wakes the session's
  waiters, so a revoked `message_wait` ends immediately. The session and threads stay (R5). A
  session with no approved credential is marked as such on its threads and on the registrations
  page.

## Passkeys and browser sessions

The predecessor's design carries forward, with these changes:

- `@simplewebauthn/server` with user verification required and discoverable credentials. Sign-in is
  usernameless: begin returns a challenge with no allowed credentials, so it reveals nothing about
  who exists. Before any operator exists, the sign-in page says to run `agention passkey-link`.
- Finish reads a null in a member that WebAuthn allows to be null as that member left out, and
  ignores `clientExtensionResults`, which neither the server nor `@simplewebauthn/server` reads and
  which passkey managers such as 1Password leave out of a sign-in.
- Challenges are stateless, so no flood can use them up. Begin writes nothing: it seals the
  challenge, its kind and a five-minute expiry with the instance's challenge key (HMAC) into a
  `__Host-` cookie. Finish checks the seal, the kind and the expiry before it verifies the
  credential, and on success records the challenge as used until it expires, in the same
  transaction, so a successful ceremony cannot be replayed. Link begin also requires a valid link
  token.
- Sign-in compares the assertion's user handle with the one stored for the credential.
- Browser sessions use a `__Host-agention-<port>-session` cookie (Secure, HttpOnly,
  SameSite=Strict), the port the origin's, and expire after 7 days idle or 30 days absolute. The
  challenge cookie is named for the port the same way.
- A new passkey's user name and display name are `<server name> · <operator>`, the server's name
  first so that an authenticator shortening a long user name keeps it; its relying party's name is
  the server's name.
- Mutations need the session's CSRF token in `X-CSRF-Token` (constant-time compare) and an exact,
  single-valued `Origin`. Requests carrying `Authorization` are refused on every web route, sign-in
  begin included.
- `agention passkey-link` (local, needs the data directory) prints a one-use link valid for 15
  minutes with its token in the URL fragment. On first use it creates the operator; afterwards it
  replaces the operator's passkeys and deletes their browser sessions, in one transaction that also
  deletes the link. Issuing a link deletes every unused one. Links come only from this local
  command, so holding a passkey never yields a link. Its `--operator-name` names the operator a
  first link creates (default `operator`), so that `--name` always means the server's name.

### Several passkeys

The operator may hold several passkeys and manages them on a passkeys page:

- The operator holds at most 20 passkeys; adding a 21st is refused at begin and again inside the
  finishing transaction (`invalid_input`), so ceremonies running side by side cannot pass it. Every
  passkey has a name (plain, 1-50, single line), given when it is added and changed at any time. A
  browser session records the passkey that signed it in (`passkey_id`, deleted with it), and signing
  in stamps that passkey's `last_used_at`.
- **Recent sign-in.** Adding a passkey and removing one need a browser session created within the
  last 10 minutes; otherwise they answer `not_allowed`, and the page offers to sign in again, which
  replaces the session. Renaming needs no more than being signed in. Sessions are only ever created
  by a passkey ceremony, so a recent session means a recent user-verified passkey.
- **Add on this device**: a registration ceremony (`add` challenge kind) whose options carry the
  operator's user handle and exclude the credentials already held, so a device cannot add the same
  passkey twice.
- **Another device** signs in with a passkey the operator holds (the browser's cross-device sign-in)
  and adds its own; a device that cannot is added by `agention passkey-link`, which replaces every
  passkey (ruling 44).
- **Remove**: refused (`invalid_input`) for the operator's last passkey. Removing one deletes it
  and, with it, every browser session it signed in, the caller's own included, in which case the
  page returns to sign-in.
- The list shows each passkey's name, when it was added and last used, and which one signed in this
  session.
- `--origin` is canonicalized at startup: `https`, a domain name (browsers refuse passkeys for an IP
  address), no path, query, fragment or explicit default port.

## Rate budgets (R31)

Token buckets in a small module of our own, never keyed on source address:

- Requests signed by a key the server knows, pending or approved, are budgeted per key, so an agent
  waiting for approval and checking with `register` spends only its own budget. The map grows only
  with registrations, which the submit bucket limits.
- Everything else is budgeted by one global bucket per class: submits that create a registration,
  other failed agent authentication (unknown keys, bad signatures, thread calls from unapproved
  registrations), failed sign-ins, and failed links (a bad link token at begin, or a failed finish).
  Every bucket but the submit bucket is charged only on failure, after the request has been checked,
  so draining one never refuses a valid key, passkey or link; a drained bucket answers
  `rate_limited` only to further failures. Ceremony begins cost nothing, since they write nothing.

The bridge returns `rate_limited` as a tool error like any other. The rates are constants chosen in
code review and documented in the operator guide. Tests drain each class and show the others,
approved agents, and pending agents checking their registration still answer.

## Pruning

Expired used challenges, links and browser sessions are deleted whenever their table is next
written; rows arrive only from successful ceremonies, the operator's links and one operator's
sessions, so no timer is needed. Registrations that expired while pending go the same way when the
registrations table is next written, so a flood of submits cannot accumulate. Logs and decided
registrations are never deleted.

## `agention serve`

- Flags: `--data`, `--origin`, `--listen`, `--tls-cert` and `--tls-key` (both or neither),
  `--allow-plain-http` (needed for plain HTTP on a non-loopback address), and `--quiet-minutes` (1
  to 10,080, default 15), after which a session not seen is quiet, and `--name`, the server's name
  (1 to 40 characters on one line, with no control characters).
- The name is set once. The first start to serve stores `--name`, or `Agention` without it, in the
  `instance` row once it is listening, so a start that fails before serving leaves the name unset;
  every later start reads it from there and may leave `--name` out or repeat it, and one naming
  another is refused, saying the server's name. The database refuses changing a set name. The web UI
  shows it as its title, and a passkey made on the server carries it, as its relying party's name
  and in its user name.
- Several servers may run on one host under different ports, each with its own data directory,
  `--listen`, `--origin` and name. A browser keeps one set of cookies for a host whatever its port,
  so each server's cookies carry its origin's port in their names (`__Host-agention-443-session`),
  and each reads only its own; a passkey belongs to the host name, so the user name each carries,
  `<server name> · <operator>`, tells them apart in the browser's list. The guide shows a second
  server on its own machine, the likely setup, and mentions sharing a host only in passing.
- Plain HTTP on a non-loopback address without the flag exits with an error naming it (R30). No
  forwarded or identity headers are read.
- The web UI is the Vite build of `apps/web`, served from the server package's `web/` directory with
  the SPA fallback for non-API routes. When it was not built, a placeholder page says so. The server
  writes its name, HTML-escaped, into the page's `<title>` and its `application-name` and
  `apple-mobile-web-app-title` metadata as it serves the page, and the web UI reads it from there.
- `Host` must equal the origin's host on every route. Security headers carry forward, with the CSP
  tightened to:

  ```text
  default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; connect-src 'self';
  base-uri 'none'; form-action 'self'; frame-ancestors 'none'
  ```

- Server timeouts: request headers 10 s, whole request 30 s, idle keep-alive 120 s. A long poll ends
  on its own deadline (25 s at most).

## HTTP API

Both mounts take and return JSON with a 2 MiB body limit; a body must declare its length, so nothing
is read before authentication (a chunked body answers 411), and the thread routes are one Hono
sub-application mounted on each, so role and message checks are shared.

Agent machines run whatever bridge version their plugin pins, so once a bridge is released the agent
routes only grow: a change adds routes or optional fields and never removes or redefines one. A
message is sent as
`{request_id, seen_through, text, detail, references, asks, answers, withdrawals, topic, replaces}`,
every field after `seen_through` optional and `detail` only beside `text`: `asks` a list of asks as
the bridge's tools describe them below, `answers` a list of `{ask, declined: true}` or
`{ask, picks, text}` with at least one of `picks` (suggestion indexes) and `text` (the answerer's
own words), `withdrawals` a list of `{ask, reason}`, `ask` an ask's number, and `replaces` a
sequence. Reads return each ask with its `number` and, once withdrawn, its `withdrawal`; each thread
with its `status`; and each answer as
`{ask, question, ask_seq, ask_live, declined, picks, labels, text}`, where `question` is the ask's
question, so a reader without the asking message knows what each answer is for, `ask_seq` is the
message carrying the ask and `ask_live` whether that message is still live. `thread_create` takes
`request_id`, `title` and the same optional parts but `answers`, `withdrawals` and `replaces`.
Request schemas ignore fields they do not know, so a newer bridge works against an older server for
everything that server supports; a route the server lacks answers `not_found`. Upgrading the server
before the plugins keeps every field honored.

Cursors are opaque keyset positions. The long poll returns at once with the threads in the session
that have unread messages (as [Read and archive marks](#read-and-archive-marks) defines them) and,
when `since` is given, a message with a later `session_pos`, each such thread once, ordered by its
latest message's `session_pos`; a full page's `since` is the position of its last thread's latest
message, so the next call continues after it. Otherwise it waits on the session's notifier until
such a message commits, the credential is revoked, the client disconnects or the wait ends. `since`
is the session position the result covered; one beyond the session's latest position (a restored
database, another session's value) counts as absent, so nothing unread is skipped.

## Agent bridge

`apps/bridge` is published as `@wayfarerlabs/agention-mcp`: one esbuild bundle with no runtime
dependencies, run by `npx` from the plugin's MCP entry. It is a stdio server on
`@modelcontextprotocol/server`, which negotiates the protocol versions both hosts use today.

### Configuration and session

- The bridge needs Node 24 or later (its package's `engines` range and esbuild target) and checks
  the version at startup, exiting with a message that names it.
- `AGENTION_URL` names the server. The bridge canonicalizes it exactly as the server canonicalizes
  `--origin` (`https`, a host, no path, query, fragment or explicit default port) and refuses
  anything else, so tokens and message text never travel over plain HTTP and `aud` always matches.
  Without it, every tool answers with an error saying to set it. A server with a certificate from a
  private authority works through Node's own `NODE_EXTRA_CA_CERTS`.
- The bridge takes its session from the first `register` call's `agent` and `session` arguments,
  else from `AGENTWORKS_AGENT` and `AGENTWORKS_SESSION` (R36); whichever is used first fixes it. A
  later `register` naming a different session is an error: one bridge process serves one session. A
  tool called before any names are available answers with an error saying to call `register` with
  names.
- The key lives in `~/.config/agention/<server>/<agent>/<session>/key.pem` (PKCS #8), where
  `<server>` is the origin's host (and port, when not 443) and the names are the proposed ones. The
  path is fixed, so both hosts find the same key whatever environment they pass. The key's
  directories and file follow the server's private-file rule (Opening), below a home directory that
  must exist. It is the bridge's only state. Sessions whose keys share a home directory are not
  isolated from one another: a `register` naming another session uses that session's key, so agents
  that must not act as each other run as different users.
- A new key is written to a temporary file and linked into place, which fails if a key already
  exists, so two bridges starting together in one session end up sharing one complete key. The
  bridge reads the file for every request, so bridges sharing a session always sign with the current
  key.

### `register`

`register` takes optional `agent` and `session` names and follows the HLA's registration flow. It
reads the key, generating one if the file does not exist, and makes the registration request. Its
answer carries the registration's expiry only while it is pending, so an agent never reads it as the
credential's:

| State                        | Answer to the agent                                                                                                           |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Approved                     | Registered as the granted agent and session, which every later call uses                                                      |
| Pending, new or existing     | Ask the operator to approve code `XXXXX-XXXXX` for `<agent>/<session>` at `<origin>/registrations`                            |
| Rejected, expired or revoked | The key file is replaced and a new registration submitted; the answer says which of the three happened and gives the new code |

Only `register` creates or replaces a key. It replaces the file only while it still holds the key
the server refused, writing the new one by rename, and after submitting it re-reads the file: if
another bridge replaced the key in the meantime, it reports the registration for the key now on
disk, so the code the agent relays belongs to a key a bridge holds. A registration left behind that
way was never relayed and expires unapproved. Only two replacements interleaving within one network
round trip can relay a code whose key was overwritten; if the operator approves it, the session's
next `register` shows the key on disk still pending, and the operator revokes the stray one. Calling
`register` at the start of every conversation is cheap and safe; the skill says to.

The bridge keeps the granted names in memory. When a tool runs before `register` in a process whose
key file exists, the bridge makes the same registration request once to learn them. For a key the
server knows, that request creates nothing; for one it does not (a submit that failed after the key
was written), it registers the key exactly as `register` would have. The bridge never creates or
replaces a key outside `register`.

  refuses a field it does not know (`invalid_input` naming it), so a misspelled field never drops
  silently; the server's own request schemas stay lenient, for a newer bridge.
- `asks` is a list of up to ten
  `{question, suggestions [{label, description}], multiple, impact, priority, effort, answer_by, fallback}`,
  the shape of the question tools agents already use, with Agention's attention fields. Its
  description says that each ask is numbered as it is written, that asks belonging together go in
  one message and the operator may answer them together or apart, and that replacing an asking
  message asks again under new numbers. `withdrawals` is a list of up to ten `{ask, reason}`, and
  its description says to withdraw an ask no longer needed, saying why, and that a withdrawal is
  never undone. The bridge offers no way to answer, since a session is never an audience in v1; the
  shared route refuses an answer from the requester in any case.
- A message in a result carries its fields, whether it is live and what replaced it; for each ask,
  its number, whether it is open, and its live answer with the picked labels or its withdrawal; for
  each answer, the number and question of the ask it answers and whether that ask is still live. An
  answer's `text` is the operator's own words on the ask, apart from the message's `text` and
  `detail`, which are any additional information; the tool descriptions say so.
- A replacement is a whole message: it carries again every part it keeps (text, detail, references,
  asks, topic, withdrawals), or what it leaves out is gone, except that it can drop no open ask,
  which is withdrawn instead. The tool descriptions and the skill say so.
- A successful call returns the API's JSON as the tool's text. A call the server refuses is an error
  result whose text is the API's error JSON; the server's `unauthenticated` message tells the agent
  to call `register`, which reports what the operator still has to do. A problem the bridge finds
  itself (its configuration, an unreachable server, missing names, a cancelled call) is an error
  result in plain text, worded for the agent: what to do, or, for what only the operator can fix, to
  tell them at the terminal what to change, with whether the session must restart (ruling 62).
  Agention answers its own failures in its JSON, so a server error without it is a proxy's, such as
  `tailscale serve` while the server behind it is stopped, and says first to check that the server
  is running.
- Every tool is annotated `destructiveHint: false` and `openWorldHint: false`, and none claims to be
  read-only, since each thread tool will carry the session envelope. That is true of them: messages
  are append-only, a key is replaced only after the server refused it, and the bridge talks to one
  configured server. Codex's default approval mode runs tools annotated this way without a prompt,
  so the plugin overrides no approval policy; Claude Code asks the operator to allow the server's
  tools once.
- A tool's text stays within what both hosts pass to the model whole, so no host cuts it mid-JSON or
  moves it to a file (see the host rows in the prior-art research):
  - a result is at most 40,000 bytes of UTF-8 JSON, under the 48,000 bytes Codex keeps by default
    and the 50,000 characters Claude Code keeps inline. Each tool declares that limit as
    `_meta["anthropic/maxResultSizeChars"]`, which also exempts its text from Claude Code's token
    limit;
  - an error's text is at most 10,000 bytes, under the roughly 11,000 characters of error text
    Claude Code keeps whole: a `stale` error by trimming, every other by construction, since each
    value it quotes is bounded (the origin by DNS lengths, the key path by a home of at most 4,096
    bytes) or shortened to 100 characters;
  - `thread_create` and `message_send` return the API's write result (see Writes), never text;
    `thread_get` shows the rest.
  - Paged results (`thread_get`, `thread_list`, `message_wait`) are repeated with half the page size
    until they fit, down to one element, so the cursor always moves forward.
  - A `stale` error keeps only the leading missed messages that fit and says from which sequence to
    read the rest with `thread_get`.
  - If a result still does not fit, its largest text-bearing fields (texts, details, references,
    fallback text, questions, suggested answers) are left out, largest first, each named in an
    `omitted` list, until it does. A text and a detail of one-byte characters that JSON need not
    escape at their bounds always fit; a detail in other scripts can be left out from roughly 19,000
    code points (two-byte scripts) down to about 9,500 (emoji), as can several large fields at once.
    The web UI shows everything in full.
- `message_wait` with `wait_seconds` 0 answers at once with what is unread, which is how an agent
  checks for answers as it works (ruling 48); its description says that a longer wait is for an
  agent with no other work and open asks or unread messages, or for a waiter of the agent's own,
  such as a subagent (ruling 61). Its 25-second ceiling leaves headroom under Codex's 60-second
  default tool timeout: only its first request waits, a smaller page that a result over the cap asks
  for after it answers at once, and the whole call, its credential lookup included, has its wait and
  one answer's 30 seconds to finish. A failed wait, for any reason but invalid input or cancellation
  (the server unreachable, `unauthenticated`), answers no sooner than its `wait_seconds` would have
  ended, so a waiter of the agent's own, waiting through an outage, calls once per wait rather than
  as fast as it can.
- Tool descriptions state what each priority level means, which fields are Markdown, what a
  message's text and detail each carry (ruling 53), and that an ask is revised by replacing its
  message and withdrawn, with a reason, by a later message or by the replacement revising its
  message's other asks, and what impact `blocking` means (the work the ask is for stops, while the
  agent carries on), so the skill can stay short (R35).

The host behavior this section relies on (environment passing, protocol versions, Codex's tool
approval) is in the [prior-art research](prior-art-research.md)'s host rows, from a prototype run on
both hosts.

## Plugin and skill

- The canonical definition declares one MCP server, `agention`:
  `npx -y @wayfarerlabs/agention-mcp@<version>`. The Claude Code plugin's `.mcp.json` carries it as
  is. The Codex plugin adds `env_vars` (`AGENTION_URL`, `AGENTWORKS_AGENT`, `AGENTWORKS_SESSION`,
  `NODE_EXTRA_CA_CERTS`), because Codex passes a server only the variables it lists.
- The version is the release version. The canonical definition names the package alone and the
  generator appends the plugin's version; release-please updates the generated MCP entries through
  `extra-files` JSON paths, and its JSON updater replaces the version inside a string, so
  `@wayfarerlabs/agention-mcp@0.1.0` stays one argument.
- The generator takes a development override of the bridge's package arguments and renders into a
  directory that must not exist yet, which it creates, so the render can overwrite nothing. Before
  the first release publishes the bridge, live runs install a plugin rendered against a packed
  tarball (`npx -y --package=<file> agention-mcp`; npm 11 runs a bare tarball path as a command, not
  a package). The package arguments are the only difference from the committed plugin.
- The skill opens, in its description, which hosts list before the skill loads, and in its body
  (R35), with the rule (ruling 60) that every question, decision or approval the agent would put to
  its user, whatever calls for it, goes to the operator as an ask, and that the agent never waits at
  the terminal for an answer, neither through a question tool that waits (`AskUserQuestion` in
  Claude Code, `request_user_input` in Codex) nor by ending its turn to wait, until the operator
  says otherwise. The description says to load the skill whenever the agent uses Agention (ruling
  61). Since the operator may follow the terminal alone for a while, whatever the agent sends the
  operator in Agention it also shows at the terminal, and carries on: in its output, or with a
  question tool that does not wait, such as Codex's `request_user_input_async`, which posts its
  questions and returns at once. When something needs the operator at the terminal, such as leaving
  plan mode, the agent asks for it through Agention.
- The bridge's answer to `initialize` carries instructions with the same rule (ruling 60), so the
  agent has it before the skill loads, and tells the agent to load the skill first. Claude Code adds
  them to the agent's system prompt, and Codex describes the bridge's tools with them, showing only
  their first 250 characters until the agent loads the tools (codex-cli 0.170.0), so they stay
  within 250. `register`'s answer, once approved, says how answers reach the agent, which the skill
  follows (ruling 61): with polling, v1's only method, only when it checks.
- The skill's hard rules include calling `register` first in every conversation, with stable agent
  and session names when the environment supplies none; a fresh random request id for every write,
  since several credentials can act as one session (the tools' descriptions say a retry reuses it);
  and never blocking, so the agent carries on with work that does not need the answer (ruling 48):
  it checks for answers as it works (`message_wait` with no wait) and checks for itself what it can
  see (a pull request's state, a deploy's). Once its other work is done, it keeps running while it
  has open asks or unread messages, and stops when none remain or the operator tells it to (ruling
  61). It checks in the way that costs least: a waiter of its own in the background where the host
  offers one, such as a subagent, which keeps the conversation small; otherwise the longest wait,
  passing `since` back, saying nothing between checks. A message without an ask is normal. It
  withdraws an ask it no longer needs answered, saying why, such as a pull request merged or its
  fallback taken once answer-by passed, and relies on an answer it can check only once it has
  checked it.
- The skill has the agent take a message whose author is a person, which is the operator's, as the
  operator's own words at its terminal (ruling 60): answers, instructions and corrections carry the
  same authority, within the same limits, and a replaced message gives way to its replacement. The
  server sets a message's author from authentication, so only the operator's passkey sign-in writes
  one; messages from agent sessions are not the operator's. The operator moves between the terminal
  and Agention as suits them, and the agent brings its threads in line with what it is told at the
  terminal, replacing an ask that changes and withdrawing one that is settled.
- The skill has every message stand on its own (ruling 53), so the operator can decide on it or
  understand it from Agention alone, without going to the agent's terminal or another source: the
  text says in a few sentences what the matter is and what is needed, and the detail carries
  everything else, such as what the agent found, the options and their tradeoffs, evidence, and
  excerpts of diffs, logs or errors, with links as references. Neither points at what only the
  agent's conversation shows ("as discussed", "the plan above"), and neither carries secrets: keys,
  tokens and passwords come out of any excerpt, since no message is ever deleted. Its example shows
  a detail.
- The skill's normal loop: `register`, and in a new conversation `thread_list` with status open for
  the asks it left open; one thread per matter, with a short topic naming the area of work, shared
  by the session's threads in that area, and an ask whenever an answer is wanted (a question,
  suggested answers with descriptions, impact, priority, and effort when the agent can judge it),
  and asks in one message only when they stand or fall together, since revising one replaces the
  message and asks them all again under new numbers; checking with `message_wait` for the operator's
  messages and answers, each answer carrying its ask's question, then `thread_read` through what was
  handled, so the operator sees how far the agent has read; revising an ask by replacing its
  message, never by asking the same thing again beside it, and sending the whole message again;
  withdrawing one with a reason; and archiving a thread once it needs nothing more. A message
  without an ask is only read, so an agent that needs an answer asks.

## Web

### UI

- Routes: `/` (the thread list, its filters, sort and grouping in the query, as
  `?unread=true&agent=…&agent=…&session=agent/session&search=…&sort=due&reverse=true&group=session`,
  and no filters, the priority sort in its own order and no grouping when absent),
  `/s/<agent>/<session>/threads/<n>`, `/registrations`, `/passkeys`, `/sign-in`, `/link`. The link
  page asks for the new passkey's name and, once an operator exists, says that finishing replaces
  every passkey and ends every browser session. The passkeys page says how to add another device:
  sign in there with a passkey the operator holds, such as their phone's, through that browser's
  cross-device sign-in, then add the device's own there. A hand-written router over the History API;
  a link token in the fragment is read once and removed with `history.replaceState`.
- The banner's tabs, Threads, Registrations and Passkeys, are the primary navigation. On a phone
  they fill their own row beneath the brand, sharing its width, and the current tab carries the
  accent and a bar along its foot (`aria-current="page"`). A thread page is within Threads, which
  stays marked there as the current section (`aria-current="true"`). After navigation, focus moves
  to the page's heading; a page with a tab is named by it, so that heading is visually hidden.
- The server's name titles the UI: the brand in the banner, the sign-in and link pages, the
  home-screen title, and each page's title after the page's own name, as `Threads · Work`. Sentences
  about the software still name Agention.
- Data hooks own loading and stale responses (an older request never overwrites a newer result).
  Views poll every 10 seconds while the page is visible and refetch on focus (R27); a paged list
  reloads every page it has loaded, from the first, and keeps one row per thread. Any `401` returns
  to sign-in, keeping the current route to come back to.
- Each write has one request id per user action. After a failure whose outcome is unknown (a lost
  connection), resending keeps the id only while the content is unchanged and the thread shows no
  message the failed attempt had not seen, so a replayed result never stands in for an answer to
  something newer. A `stale` refusal records nothing, so its resend below keeps the id.
- The thread page opens on the page holding the operator's first unread message, or on the newest
  page when nothing is unread, and loads earlier and later messages on demand. It never claims to
  have seen what it has not shown. Marking read states the last message on screen. A write's
  `seen_through` states the last message on screen when the operator began that draft, so a write
  over messages not yet loaded, or over one that arrived while the operator was writing, comes back
  stale with them and the operator sees them before it is sent.
- A stale write keeps the draft, shows the missed messages above it, and offers one action that
  marks them read and submits again with the same request id and the new `seen_through` (R29); the
  server records no refused write, so the id is still free. When the missed messages changed what
  the draft does (an ask it answers was replaced or answered, or the message it replaces was
  replaced), the text stays, each answer or the replacement that no longer fits is dropped, and the
  page says what changed before the operator chooses again; nothing is resent that no longer fits.
- Passkeys use `PublicKeyCredential.parseCreationOptionsFromJSON`, `parseRequestOptionsFromJSON` and
  `toJSON` (Safari 18.4+, Chrome 129+). A browser without them is told it cannot sign in.
- The registrations page shows each pending registration's code in a large monospace face, grouped
  as the agent relays it.
- Design tokens are CSS custom properties on `:root`, redefined under `prefers-color-scheme: dark`,
  with `color-scheme: light dark` and a matching `theme-color`. No inline styles, so the CSP holds.
- Accessibility: lists are lists and threads are links containing their headings (never headings
  inside buttons), visible focus, 44-pixel touch targets, WCAG AA contrast in both themes,
  `prefers-reduced-motion` respected, and form errors tied to their fields.

### Thread list

One list, **Threads** (rulings 37, 38, 40 to 43 and 45 to 48, and the prior-art research). With no
filter on, it shows every thread the operator has not archived, in the priority sort, ungrouped.
Grouping, sorting and filtering are separate controls.

- **Head.** The controls **Sort** with its direction, **Group**, and then **Filters**, in that order
  on screen and for focus: on one row where they fit, and otherwise Sort and its direction on one
  row with Group and Filters beneath, the direction wrapping beneath Sort on the narrowest phones or
  with enlarged text. Its heading, **Threads**, is visually hidden, as [UI](#ui) says. Group is a
  native select (Flat, Session, Agent), named "Group", beside a grouping icon; Sort is a native
  select (Priority, Due, Effort, Latest message, Created), named "Sort", beside a sort icon. The
  direction is a button beside it that names the order in words beside an arrow and reverses it when
  pressed: Most pressing first or Least pressing first, Soonest first or Latest first, Quickest
  first or Longest first, and Newest first or Oldest first for both Latest message and Created;
  choosing another sort returns to its own order. Filters is an icon-only funnel, named "Filters"
  and, with filters on, "Filters, N on", with a badge counting them. Group, Sort and its direction
  are no filters: the badge and Reset filters leave them alone, and the thread page's path keeps
  them.
- **Location.** A thread's agent, session and topic each show behind a small letter badge, A, S or
  T, wherever they appear: rows, the thread page, group headers, chips and the sheet's labels. The
  badge is hidden from assistive technology, which hears the word instead ("Agent builder"), and
  carries the word as its tooltip. A topic beside its session shows bare; standing alone, on a chip
  or in the Topic popup, it is written `session/topic`.
- **Filter sheet.** Filters opens a sheet (a modal dialog: a bottom sheet on a phone, a panel on a
  wide screen) holding every filter, one row per dimension with concise labels and values, each
  enumerated one a segmented control (a fieldset of radio inputs) whose first value is off:
  - Search titles (a text field);
  - Status: Any · Open · Answered · Withdrawn · None, and beneath it the properties of one open ask:
    Priority (Any · Normal+ · High+ · Urgent), Impact (Any · Blocking · Assuming), Due (Any ·
    Overdue) and Effort (Any · Quick · ≤15m · ≤1h). Choosing one of them chooses Open, and choosing
    another status clears them all;
  - Read: Any · Unread; Read by agent: Any · Unread · Stranded;
  - Agent, Session and Topic, each a multi-select popup beside its letter badge;
  - Archived: Hide · Show.

  Every value not chosen shows a count in parentheses, "Unread (4)", spoken "Unread, 4 threads": its
  count as [Counts](#open-asks-roll-ups-and-filters) defines it, from `/threads/counts`, fetched
  while the sheet is open and after each change, the last counts staying until new ones arrive. A
  chosen value of a segmented control shows none; every option of a multi-select keeps its count,
  checked or not, since checking one changes no other's. The list behind the sheet updates as
  filters change. At its foot the sheet offers **Reset filters** with the total the list holds with
  every filter off, and closes with a button saying how many threads the list holds ("Show 12
  threads"). Symbols are spoken as words ("≤15m" as "Under 15 minutes").

- **Multi-select popups.** Agent's, Session's and Topic's rows each hold a button naming what is
  chosen (Any, the one name, or "3 chosen"), which discloses a popup beneath it within the sheet: a
  search box ("Search agents") that narrows the options by what they show as it is typed, and a
  checkbox for each option, in name order, with its count. Agents, sessions and topics are those
  holding a thread. Sessions show their agent beside their name, muted, and topics likewise show
  their agent beside them, muted, so two agents' like-named topics stay apart. The popups narrow
  down the hierarchy: while agents are chosen, only their sessions are offered; while sessions are
  chosen, only their topics, or else while agents are chosen, only those agents' topics; the
  narrowing never hides an option already chosen. Each takes at most 50 choices, the bound on a
  filter; at 50 the boxes not checked are disabled and the popup says so. Escape, Done or a tap
  outside closes the popup and returns focus to its button, as the message options do.
- **Chips.** Under the head, each filter that is on is a removable chip with a terse label. Agent's
  shows its badge and "reviewer" while one is chosen and "3 agents" while several are, and Session's
  and Topic's likewise. A chip fits its text up to 20 characters, a badge counting as two, and past
  that is cut to 19 with "…", a chip with a badge at its front so its end stays and any other at its
  end; its spoken label ("Agent reviewer", a topic's whole `agent/session/topic`) is its tooltip and
  accessible name. Chips are compact, about 28 pixels tall with a small corner radius, so a row of
  them stays short; as the operator chose, their targets meet WCAG 2.2's 24-pixel minimum rather
  than the 44 pixels used elsewhere. Removing one clears its filter and moves focus to Filters. The
  row wraps rather than scrolling sideways.
- **Read and archive icons.** Standard icons, drawn as inline SVG like the funnel and named for
  assistive technology: a closed envelope for unread, an open envelope for read, and an archive box
  for archived. A thread is unread or archived as [Read and archive marks](#read-and-archive-marks)
  defines it; a group is unread when any of its threads is, and archived when all are.
- **Rows** show the thread's number, muted ("#9"), leading the title, which is bold while unread;
  the location in body text, never as a label; while any message is unread, the closed envelope with
  the unread count over the thread's live messages ("2/5"), and otherwise the open envelope with its
  live messages ("5") (ruling 58); the archive box on a thread archived for the operator; and for a
  thread with asks open to the operator the question of its lead ask, with its priority, blocked,
  assuming and effort marks ("Quick", "≤15m", "≤1h", ">1h") and how many more are open, and, when
  any of its open asks has an answer-by, the earliest of them, whichever ask carries it and whatever
  the filters keep (ruling 57), in the browser's locale: "Due 3:00 PM" when it falls today, "Due Nov
  12, 9:00 AM" on another day, with the year when it is not this year's, and once the summary says
  it is overdue, "Overdue since 3:00 PM" as a warning, with the full date and time in its tooltip;
  otherwise its status, muted, when answered or withdrawn ("Answered", or "Withdrawn: Merged at
  14:02" with the latest withdrawal's reason on one line). A stranded thread shows a muted
  "Stranded" mark, named, while its session is quiet, for when the agent was last seen ("Stranded:
  agent last seen 14:02"); a session without an active credential is explained by its No active
  credential tag.
- **Groups.** Grouped by session, the list folds inline under session headers (agent and session),
  and under each, when its threads carry two or more topics, topic headers, those without one under
  "No topic". Grouped by agent, it folds under agent headers, and under each, when it has two or
  more sessions, session headers. Depth shows through header styles rather than indentation: the
  outer header is a sticky, tinted bar and the inner a light subheader. Each header is a heading
  wrapping a disclosure button (`aria-expanded`) whose name carries its roll-up ("Agent reviewer
  Session main, 12 threads, 3 unread, blocked on you, high priority"), and shows the roll-up
  collapsed or not: the thread count, the closed envelope with the number of unread threads when any
  is and the open envelope when none is, a blocked mark when any is blocked on the operator, the
  highest open priority, the archive box when all are archived, and on a session's or agent's header
  "last seen 14:02" or "never seen", muted, while it is quiet; an agent is quiet while every session
  it shows is. The grouped list is the one list with `group`, paged as ever, its rows arriving group
  by group with the roll-ups beside them; the page folds rows under their group's header whichever
  page brought them, so a header can stand with its roll-up before all its rows have loaded. Every
  header starts expanded; collapse state is kept in the browser's storage per device, grouping and
  header. A collapsed header hides everything under it.
- **Bulk.** **Archive all read**, archiving the loaded threads that have nothing unread, while
  archived threads are not included, skipping threads holding an open ask and saying so, and with
  Unread on, **Mark all read**; both act on the threads loaded and say when more remain.
- A filter change replaces the history entry, and the search box applies its text after a pause in
  typing. When the thread page goes back after sending, the list says the message was sent.

### Thread page

The thread page follows email: what is on screen is read, actions on the thread as a whole sit in
its head, and answering happens on the message that asked (rulings 31 to 34).

- **Head.** A back button leads the head: a heavy arrow and the word **Threads**, at full strength
  and bordered like the head's other buttons, named "Back to threads" for assistive technology. It
  returns to the list as the operator left it, with its filters; a page opened directly goes back to
  the list with none. The heading leads with the thread's number, muted, as rows do. Under it, the
  location links each part to the list narrowed to it alone, a topic by its `agent/session/topic`
  path, with no other filter on, showing everything there, in the list's sort. Under it, muted, the
  thread's status when answered or withdrawn, as rows show it; and on a thread stranded by a quiet
  session, that the agent was last seen at a time and has not read the operator's latest messages (a
  session without an active credential shows its tag). Beside the title sits **Archive all**, which
  first shows every message through the latest, then archives through it, is unavailable while an
  ask is open to the operator and says why, and returns to the list, as email does. The head shows
  the archive box while the thread is archived for the operator. When asks are open, a count jumps
  to the next of those the thread's roll-up lists, loading its page when needed.
- **Options.** Each live message has a ⋯ options button ("Options for message N") that discloses its
  uncommon actions as buttons; Escape, choosing an action, a tap elsewhere or focus moving on to
  another control closes it, and one is open at a time. Closing returns focus to its button without
  scrolling, unless the tap or focus landed on another control, which keeps it. **Mark unread from
  here**, on every live message after the archive mark, marks the operator's read cursor back to
  just before it and returns to the list, as email does, so the page does not read the thread again
  at once. **Archive through here**, beside it on every live message the archive mark has not
  reached, archives that message and every earlier one. It is unavailable while an ask open to the
  operator sits in that message or an earlier one, and names the earliest, from the thread's
  roll-up, to answer or decline first. The page stays, with the archived messages folded; leaving is
  Archive all's. **Change answer** is on a message carrying the operator's answers while any ask it
  answered is still live, and **Edit** on the operator's other messages.
- **Archived messages.** Messages at or before the operator's archive mark fold into one line at the
  top, "5 archived messages" with the archive box, which expands to show them, each with the archive
  box; the page opens below them and never reads them while folded, and shows them when a staged
  change of answers reopens a card among them. Archiving reaches only messages the page has shown. A
  message the operator sends while the thread is archived for them stays in view until they leave
  the page, though it is archived with the rest.
- **Reading.** While the page is visible, it marks read through the last message on screen whenever
  that is beyond the operator's cursor: on opening, when a refresh shows new messages, and when
  later messages are shown on request. Each of the agent's messages shows the closed envelope,
  accented, if it was unread when it first appeared, and the open envelope otherwise, until the
  operator leaves the page; the first of a run of unread ones also gets a "New" divider. Each of the
  operator's live messages shows the agent's reading at the card's foot, on the right, small and
  muted: the envelope, closed and accented while the message is beyond the agent's read cursor and
  open once it is not, then the word "agent", named "Unread by agent" or "Read by agent" (ruling
  47). The card's head carries only the operator's own reading. A failed mark shows its failure and
  is tried again on the next refresh.
- **Messages.** Each shows its author, time, text, references and any topic it set. A message's
  detail is one folded **Details** line directly under its text, which opens in place and stays open
  across refreshes while the page is open; folded, it is never parsed (see Markdown). A replaced
  message collapses to a line naming the message that replaced it, which expands to show it; a
  replacement names what it replaces, and one that carries nothing reads as a retraction. A message
  carrying answers says, for each, which ask it answers and what was chosen in the card's own terms
  ("Answered ask 3: Postgres"): the picked suggestions, and **Other** when the operator chose it,
  with their words beneath; the words alone on an ask without suggestions; or that they declined. An
  answer to an ask its requester since revised or retracted says so. A message carrying withdrawals
  says, for each, "Withdrew ask 3: " and the reason.
- **Asks.** An ask is a card on its message, several to a message: its number ("Ask 3") leading the
  card, the question, the priority, impact, effort, answer-by and fallback text, and its state:
  open, answered (showing the picked suggestions and Other with the operator's words, the words
  alone on an ask without suggestions, or that they declined), withdrawn, with its reason and the
  message that withdrew it ("Withdrawn in #7: Merged at 14:02"), or revised by a replacement. On an
  ask open to the operator the card is where the answer is written, following the form conventions
  in the prior-art research:
  - The question is the group's legend. Suggested answers stack under it with their descriptions, as
    radio buttons under "Choose one" or as checkboxes under "Choose any that apply".
  - The last choice is always **Other**. Choosing it opens a text field beside it for the operator's
    own words, which become the answer's text; where several may be picked, Other combines with
    picks.
  - An ask without suggested answers shows only a text field for the answer.
  - **Decline to answer** is a smaller link below the choices, never one of them. Choosing it sets
    the choices aside, says the ask will be declined, and offers to undo.
  - On a live ask the operator answered, **Change answer** in the options of the message carrying
    the answer.
- **Composer.** A message box at the foot, labelled **Additional information** while an answer is
  being written and **Message** otherwise, the **Details** box below it, and one **Send** button.
  Send is available only when there is something complete to send: answers (each a pick, Other or
  the answer field with words, or a decline), text in the box, or both, which go as one message. An
  answer that is started but incomplete (Other chosen without words) keeps Send unavailable and says
  why at its field. A line above the box names each answer, changed answer or edit that Send
  carries, in the card's terms and by ask number ("Ask 3: Postgres · Ask 4: Declined"; Other, never
  "own words"), each with a way to remove it that also clears its card; a staged replacement is
  removed whole, since it must answer its asks again.
  - Beside Send, a checkbox **Go back after sending**, checked unless the operator unchecked it on
    this device. The choice is kept in the browser's storage, and the default holds where storage is
    unavailable. While it is checked, a message the server accepts returns to the list as the back
    button does; a refused write stays on the page with its draft.
  - Any number of open asks' cards may hold answers at once, up to ten, and Send carries them all.
  - A **Details** box, folded under the message box until opened, holds the message's detail (ruling
    53). Neither box cuts what is typed or pasted into it: over a box's bound, or with detail but no
    text, Send is unavailable and the box says why; over the message box's bound, it says that the
    rest belongs in Details.
  - **Change answer** turns the card of every ask that message answered and that is still live back
    into choices with the operator's answers loaded, and puts that message's text and detail in the
    boxes, as a replacement of it that answers those asks again; the staged line says when an answer
    it held was to an ask since revised or retracted, which goes with the replaced message. **Edit**
    loads the message's text and detail as a replacement. Since a replacement is a whole message,
    both are unavailable while anything is being written, and say so; while one is staged nothing
    else can be started until it is sent or removed, and removing it clears what it loaded.
  - A replacement always carries text or an answer: the page never sends a retraction, and a message
    that fails to load stages nothing and says so.
  - Sending without answering an ask open to the operator asks for no confirmation in v1 (an FRD
    open question).

### Markdown (R14)

Parsing uses `mdast-util-from-markdown` with only the GFM strikethrough, table and task-list
extensions. `remark-gfm` is not used because it cannot turn off autolink literals, which would make
bare URLs into links, or footnotes, which generate relative links and IDs. An Agention component
renders the syntax tree to React elements:

- raw HTML nodes render as text (block-level ones in a paragraph that preserves line breaks);
- images and image references render as links labelled with their alt text, or their URL when there
  is none, subject to the link rule; an image inside a link renders as its text;
- a link is live only for an absolute `https` URL with a host and no user information, at most 2,048
  characters; its `href` is the parsed URL, with `rel="noopener noreferrer nofollow"` and
  `referrerpolicy="no-referrer"`, and when its text is not its own URL the link's host follows it,
  since a phone cannot preview where a link goes; anything else renders as its text;
- headings render two levels below the page's own heading, capped at the lowest level;
- code blocks carry no class derived from their info string, so a writer cannot reach the UI's
  styles;
- task-list checkboxes are disabled; table alignment maps to fixed classes.

Agent text cannot take the whole UI down, though it can stall one thread's page, an accepted risk
described below. Each Markdown field renders inside an error boundary that falls back to its text
with line breaks kept, and the app has a boundary of its own. Text with a line that opens more than
32 nested blocks (quotes or list items) renders that way without being parsed, because the parser's
cost grows faster than such text, and the renderer stops descending 32 nodes deep. Some constructs
still parse in more than linear time, quadratically within one paragraph: long runs of emphasis
delimiters take about 2.5 seconds in Node and 1.5 seconds in Chromium for one field at its
20,000-code-point bound, which only a detail reaches. A text at its 1,000-code-point bound takes
under 10 milliseconds, so a thread page's 50 texts cost well under a second, and the page parses a
detail only when it is opened, so deliberately hostile text can stall one thread's page for a second
or two for each detail opened. The lists render no Markdown, so the operator can still reach the
registrations page and revoke the session's credential.

Plain fields (title, questions, suggested answers and their descriptions, an answer's own words,
fallback, topics, reference labels, names) render as text nodes and never pass through the parser;
multi-line plain fields keep their line breaks. Reference URLs follow the same link rule. The CSP's
`img-src 'self'` backs up the image rule. Component tests cover each rule with the hand check's
inputs plus `javascript:`, `data:`, entity-obfuscated schemes, autolinks, reference-style images,
credentialed URLs, info-string classes, and deeply nested quotes and lists.
